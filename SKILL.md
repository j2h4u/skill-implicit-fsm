# Implicit FSM Discovery, Contract Refinement and Implementation

This is a multi-purpose skill spanning connected domains:

- **Specification mining:** recover behavioral contracts from code, tests and executions; separate observed behavior from intended requirements.
- **Invariant refinement:** make implicit properties explicit, challenge their validity and product relevance, and preserve justified requirements in a traceable registry.
- **Design and implementation — the primary axis:** discover implicit FSMs and implement justified candidates as explicit machines, transition tables or state/event matrices with defined transition semantics; make behavior deterministic where the contract requires it and separate effects.
- **Continuous improvement:** turn findings into verified project improvements and use execution feedback to refine the method when requested.

These axes form one workflow: reconstruct → challenge → design → implement → verify. Current implementation is evidence, not the specification. A full FSM request follows the entire sequence, starting with discovery. A discovery-only request returns the FSM map and preliminary dispositions; an invariant-only request reconstructs the relevant FSM context and then follows the contract stages without forcing full repository conversion. Establish whether implementation is requested; keep target code unchanged during discovery and audit, then complete authorized changes. Write audit artifacts separately. Reproduce scenarios in isolated fixtures; operating live services requires explicit authorization.

1. **Scope → FSM discovery and map.** Establish the product goals, external contracts, discovery boundary and code revision; separate confirmed sources from reconstructed hypotheses. Find implicit FSMs, including distributed state and interactions. Record each candidate's stable ID, purpose, state representation, inferred states, events, guards, transitions, effects, source locations and modeling gaps. Distinguish existing explicit machines from implicit candidates. Record discovery coverage and omissions; a property-review limit does not establish FSM-discovery completeness. Do not skip reconstruction by jumping directly to a list of invariants.

2. **Contract extraction + critical refinement → R0.** Link candidate invariants, safety/liveness properties and environmental assumptions to the mapped FSMs and their interactions; retain relevant product-wide properties that do not belong to one machine. Distinguish implementation guarantees, sampled observations, inferred intentions, external requirements and possibly incidental constraints. Preserve inference scope, preconditions and sampled populations; check whether conditions were exercised, not merely unviolated. Examine necessity, usefulness, sufficiency, consumers, exceptions, redundancy, conflicts and missing requirements. Record implication under matching assumptions before suppressing redundant candidates; retain provenance. Logical implication does not authorize removing a product requirement. Assess actual compliance separately from product justification. Unknown purpose does not imply redundancy; progress claims require explicit environmental assumptions.

3. **Independent research → R1.** Assign one fresh-context subagent per property; parallelize within available capacity. Supply the property, definitions, scope, assumptions, revision and access to the whole codebase and primary requirements; omit prior verdicts and persuasive rationale. Trace producers, mutators, consumers and breakers across the product. Where feasible, validate trace-derived candidates on executions or inputs not used for inference; independent agent context is not independent data. Return supporting and opposing evidence, exceptions, dependencies, consequences, actual coverage and gaps. The coordinator reconciles reports into R1.

4. **Adversarial audit → R2.** Use new fresh-context subagents per R1 property, with the same verdict-free briefing as research, to challenge compliance, necessity and sufficiency: counterexamples, required scenarios the constraint blocks, and invalid scenarios its relaxation admits. Seek small reproducible cases where feasible. Assign a separate fresh-context review of the entire registry as one contract, including cross-group conflicts and requirements absent from R1; use related groups and end-to-end scenarios to check compatibility, reachability and progress. Findings are not mandatory. Reconcile into R2.

5. **Adjudication → Rfinal.** Resolve disagreements by evidence, never votes. Keep two axes: implementation compliance and product justification. Classify properties as relevant / redundant / contrary to confirmed goals / unresolved, with reasons; list missing requirements separately. Distinguish implementation defects, formulation defects and requirement defects. A failed proof obligation need not be a reachable violation; a violation need not invalidate the requirement. Preserve counterexamples and reassess dependent claims after refinement. Distinguish observed, tested and mechanically verified claims, including model assumptions and bounds. No counterexample found is a bounded search result; confidence is not evidence. Report unresolved questions, coverage limits and proposed actions.

6. **FSM disposition → explicit implementation and verification.** For each mapped candidate, recommend conversion, simplification, retention or further investigation, with expected benefit, complexity and contract dependencies. When implementation is requested, execute justified changes under the refined contract using the guidance below. Report what changed, what was verified and which candidates remain deferred. Do not require conversion of every candidate or substitute generic bug fixing for the requested FSM work.

## Artifacts and independence

Use a new audit directory per run, outside target source by default. Record the revision and dirty changes; without Git, record a content fingerprint of the inspected snapshot. Do not initialize Git. Do not silently combine evidence from different code versions.

Keep the initial FSM map, immutable `R0.md`, `R1.md`, `R2.md`, `Rfinal.md`, separate agent reports and an append-only `journal.md`. Each registry entry needs: stable ID and statement; linked FSM IDs; scope, assumptions and kind; factual status; product category and basis; evidence for/against with source locations and evidence strength; dependencies/conflicts; coverage/gaps; proposed disposition; review history. Preserve lineage when splitting or merging properties. Journal: old claim/verdict → new claim/verdict → evidence → reason → report. Agents return reports; only the coordinator writes registry generations. Record later model and implementation changes without overwriting the initial map.

Use the platform's fresh-context delegation mechanism; with `spawn_agent`, pass `fork_turns: "none"` and self-contained assignments. Give agents read-only responsibility for target code and separate report ownership. If isolation or capacity is unavailable, report the limit and pending checks; role-playing in one accumulated context is not independent review. Later-discovered properties retain their actual review history, not the generation's implied completeness.

## Budget and stopping

Set the discovery scope, property limit and resource budget before fan-out; reserve capacity for whole-contract review and adjudication. Baseline: one research pass and one adversarial pass; revisit only concrete conflicts or new evidence within budget. Stop with explicit uncertainty rather than seeking consensus. Never label skipped checks as completed. When asked to trial, evaluate or improve this skill, read [EVALUATION.md](EVALUATION.md) and complete its evaluation assignment alongside requested project work. Ordinary use does not require evaluating or editing the skill.

## Project improvement — when requested

A request to audit and improve the project includes implementation after adjudication; do not stop at a registry or ask again for already-authorized fixes. Prioritize requested FSM transformations under the refined contract and complete other confirmed in-scope authorized fixes. Link changes to property IDs, fix the producing code and affected callers, and verify the relevant scenarios with independent expected outcomes. Record the changed revision and verification results separately; preserve the original audit snapshots. Leave unresolved requirement changes for the needed product decision while completing independent authorized work. An audit-only request ends with findings and proposed actions.

For each selected FSM implemented under an accepted contract, a transition table or other explicit representation is only a minimum, never sufficient completion. Provide a formally analyzable specification identifying states and initial conditions, events, guards, the transition relation, properties and environmental assumptions, with precise semantics, formal property obligations and a concrete reproducible route to checking applicable safety, reachability, deadlock and progress obligations; a table with a promise to encode it later is insufficient. Provide executable stateful property-based and model-based tests that generate inputs and event sequences during test runs; one combined suite is sufficient. Run it against the implementation and record results, coverage or explored bounds, and retained failure cases. Map model states, events and effects to runtime behavior and use independent contract-derived assertions, not the implementation as its sole oracle. Cover initial and terminal behavior, invalid or unhandled events, guard overlap, and state/effect ordering on failures where relevant; model concurrency and ordering or state the environmental assumptions that exclude them. For asynchronous orchestration, address cancellation, timeouts, retries, idempotency, concurrency and crash recovery where relevant. Use shrinking and assess state, transition and sequence coverage and observability.

Separate transitions from effects and choose the smallest representation fitting the project. Record formal-check readiness separately from obligations actually checked or proved, with assumptions, bounds and model-to-code correspondence; do not claim the entire implementation is proved. Formal proof or checking is not universally required, but the specification must be checkable. A missing or unfinished specification, checking route or mapping, or required generative tests that are absent, unrun or failing means conversion is incomplete; mapping and tests do not prove model-code equivalence. Separate contract changes from behavior-preserving refactoring. No particular formal language, solver, FSM library or test framework is mandatory.

**Python tooling example:** [Hypothesis stateful testing](https://hypothesis.readthedocs.io/en/latest/stateful.html) provides `RuleBasedStateMachine`, `@rule`, strategies, `@precondition` and `@invariant`. Its database-comparison example runs generated operations against an implementation and a separate in-memory model: adapt that structure to the refined contract for combined stateful PBT/MBT. The framework generates sequences; the agent must supply the model, implementation adapter and independent assertions. For schema-based API workflows, [Schemathesis stateful testing](https://schemathesis.readthedocs.io/en/stable/explanations/stateful/) chains requests using response data; add product-specific assertions rather than treating schema conformance as the whole contract. Neither tool supplies formal proof. Use equivalent tools for other languages; these examples are not mandatory dependencies.

**Generated-test discipline:** reset model and implementation per generated scenario, not merely per pytest function. Generate valid sequences and separate invalid-event checks; preconditions must not hide required rejection behavior. Retain shrunk failures as durable regression cases, with replay information and explicit run budgets. Check measured transition coverage rather than assuming random exploration covers the graph. Sequential stateful tests do not explore concurrent schedules; exercise relevant interleavings explicitly and control clocks and injected failures for reproducibility.
